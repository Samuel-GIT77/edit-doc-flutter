Relatório Técnico Obrigatório — Fase 1

Migração Arquitetural para MVVM em Flutter

Projeto: Editor de Documentos (edit_doc_flutter)
Arquitetura: Model-View-ViewModel (MVVM)
Ambiente: Linux Container / Flutter SDK / GitHub Codespaces
Data de Emissão: 19 de Novembro de 2026
Resumo Executivo: Este documento formaliza a migração completa do código monolítico original (desenvolvido no DartPad) para uma arquitetura robusta em camadas no Flutter. As telas de Login, Cadastro e Listagem/Home foram desacopladas em Model, View, ViewModel e Utils, eliminando o uso de setState() nas regras de negócio e adotando reatividade cirúrgica com ChangeNotifier e ListenableBuilder.

1. Mapeamento de Classes e Widgets

A tabela abaixo detalha a transição do arquivo único para a estrutura modular do Flutter:

Elemento Original (DartPad) Novo Caminho no Projeto Camada MVVM Responsabilidade e Adaptações
class Usuario lib/models/usuario.dart Model Entidade de domínio com atributos id, nome, email, senha, métodos toMap()/fromMap() e copyWith().
class Documento lib/models/documento.dart Model Entidade representativa de documento (id, titulo, conteudo, dataModificacao, autorEmail).
Configurações e Tema lib/models/services/preferences_service.dart Model (Service) Persistência do tema claro/escuro e e-mail do usuário logado via shared_preferences.
Listas globais / Mocks lib/models/services/banco_local_service.dart Model (Service) Operações de CRUD assíncronas para usuários e documentos com persistência local.

Lógica de Documentos lib/viewmodels/documentos_viewmodel.dart ViewModel Gerenciamento da lista de documentos, estados de isLoading, salvar e excluir via ChangeNotifier.

2. Alterações de Estrutura e Imports

Ao converter o código contido em um único arquivo de script no DartPad para uma aplicação estruturada em múltiplos arquivos, quatro grandes transformações foram aplicadas:

2.1. Organização de Imports e Quebra de Acoplamento Circular

No DartPad, todas as classes coexistiam em um único espaço global sem necessidade de declarações import. Na arquitetura MVVM, cada arquivo declara suas dependências estritas seguindo o princípio da dependência unidirecional:

  • Views: Importam apenas seus respectivos ViewModels, modelos necessários e validadores.
  • ViewModels: Importam a camada Model (entidades e serviços) e o pacote package:flutter/foundation.dart.
  • Models/Services: Não importam ViewModels nem Views, garantindo total independência do framework visual.

2.2. Encapsulamento e Visibilidade de Atributos

No código original, variáveis de estado eram públicas ou manipuladas diretamente nas telas. Na nova arquitetura, todos os estados internos foram privatizados com o prefixo _ (ex: _usuarioAtual, _documentos, _isLoading, _isDarkTheme) e expostos apenas via getters públicos de leitura:

// lib/viewmodels/documentos_viewmodel.dart
List<Documento> _documentos = [];
List<Documento> get documentos => List.unmodifiable(_documentos); // Protege contra mutação direta

2.3. Injeção de Dependências e Construtores Parametrizados

Variáveis globais foram substituídas por injeção explícita via construtor. Isso permite desacoplamento total, facilidade de manutenção e viabilidade de testes unitários com dados simulados:

// lib/viewmodels/auth_viewmodel.dart
AuthViewModel({
  required BancoLocalService bancoService,
  required PreferencesService prefsService,
}) : _bancoService = bancoService, _prefsService = prefsService;

2.4. Centralização de Rotas Nomeadas

A navegação antes acoplada (feita por Navigator.push(context, MaterialPageRoute(...)) com chamadas diretas aos construtores das telas) foi substituída por uma tabela centralizada de rotas nomeadas no lib/main.dart: '/' (Login), '/cadastro', '/home' e '/editor'.

3. Mudanças no Gerenciamento de Estado

3.1. Eliminação do setState() para Regras de Negócio

No DartPad, cada tela continha métodos assíncronos e executava chamadas manuais como setState(() { carregando = true; }). Ao migrar para o MVVM:

  • As Views tornaram-se passivas: elas apenas reagem a estados notificados e despacham intenções do usuário.
  • O uso de setState() nas Views foi restrito estritamente a comportamentos visuais efêmeros locais (ex.: alternar a visibilidade de senha _senhaOculta = !_senhaOculta).

3.2. Padrão Observador com ChangeNotifier e notifyListeners()

Toda a manipulação de dados, chamadas de persistência e estados de carregamento residem nos ViewModels. Sempre que o estado é alterado, o método notifyListeners() é disparado:

// Exemplo no AuthViewModel:
Future<bool> login(String email, String senha) async {
  _isLoading = true;
  _mensagemErro = null;
  notifyListeners(); // Notifica a View para desenhar o spinner de progresso

  try {
    final usuario = await _bancoService.autenticar(email, senha);
    if (usuario != null) {
      _usuarioAtual = usuario;
      _isLoading = false;
      notifyListeners(); // Notifica a View com sucesso
      return true;
    }
  } catch (e) {
    _mensagemErro = 'Falha ao autenticar.';
  }
  _isLoading = false;
  notifyListeners(); // Notifica a View com o erro
  return false;
}

3.3. Reatividade Cirúrgica com ListenableBuilder

Em vez de reconstruir a tela inteira quando o estado muda, as Views e o aplicativo raiz utilizam o widget nativo ListenableBuilder. Apenas o botão ou bloco afetado é redesenhado, aumentando drasticamente o desempenho e a legibilidade:

ListenableBuilder(
  listenable: widget.authViewModel,
  builder: (context, _) {
    final carregando = widget.authViewModel.isLoading;
    return ElevatedButton(
      onPressed: carregando ? null : _fazerLogin,
      child: carregando ? CircularProgressIndicator() : Text('Entrar'),
    );
  },
)
